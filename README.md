# Система управління бібліотекою

Клієнтський застосунок для обліку книг і користувачів бібліотеки з можливістю позичання та повернення книг.

**Демо:** https://oldiix.github.io/library-management-ts/

## Функціональність

- додавання книг (назва, автор, рік видання) і користувачів (ім'я, email);
- валідація форм: усі поля обов'язкові, рік — лише цифри та регулярний вираз для року, ID користувача — лише цифри;
- позичання книги за ID користувача через модальне вікно та повернення книги;
- обмеження: не більше 3 книг на одного користувача з повідомленням у модальному вікні;
- сповіщення через модальні вікна Bootstrap (без `alert`);
- пошук книг за назвою або автором і користувачів за ім'ям, email або ID;
- видалення книг і користувачів;
- пагінація списків (5 елементів на сторінку);
- збереження всіх даних у LocalStorage.

## Технології

TypeScript, webpack (гілка `main`) / Vite (гілка `vite-migration`), Bootstrap 5, Sass, ESLint, Prettier, Mocha, Chai,
Husky, gh-pages.

У коді використано класи та інтерфейси (`Book`, `User`, `IBook`, `IUser`), generics (`Library<T>`), модулі (ES-модулі)
та простір імен (`namespace Validation`). Весь інтерфейс генерується програмно через DOM API, в `index.html` лише
`<div id="app"></div>`.

## Структура проєкту

```
src/
├── models/            # Book, User та інтерфейси IBook, IUser
├── services/          # Library<T>, Storage, LibraryService, NotificationService
├── utils/             # namespace Validation, генератор ID, пагінація
├── ui/                # робота з DOM: компоненти форм, списків, модальних вікон
├── types/             # спільні типи та константи
├── styles/            # main.scss
└── index.ts           # точка входу
tests/                 # юніт-тести Library та Validation
```

## Запуск

```bash
npm install
npm start          # dev-сервер на http://localhost:9000
npm run build      # продакшн-збірка в папку dist
npm test           # юніт-тести
npm run lint       # перевірка ESLint
npm run deploy     # деплой на GitHub Pages
```

## Гілки

- `main` — фінальна версія зі збіркою через **webpack**;
- `vite-migration` — та сама версія застосунку зі збіркою через **Vite**.

Після перемикання між цими гілками потрібно виконати `npm install`, бо в них різні залежності.

## Порівняння webpack і Vite

Заміри зроблено на одному комп'ютері для однакового коду застосунку.

| Показник                     | webpack 5                                                                | Vite 6                                                      |
|------------------------------|--------------------------------------------------------------------------|-------------------------------------------------------------|
| Старт dev-сервера            | 3113 ms                                                                  | 390 ms                                                      |
| Оновлення після зміни стилів | 42 ms (перезбирання бандла)                                              | миттєво (оновлюється лише змінений модуль)                  |
| Час продакшн-збірки          | 3980 ms                                                                  | 871 ms                                                      |
| Результат збірки             | один `bundle.js` 320 KiB (CSS вбудовано в JS), 3 попередження про розмір | CSS 231.17 kB (gzip 30.72 kB) + JS 90.29 kB (gzip 27.86 kB) |
| Конфігурація                 | `webpack.config.js`, ~45 рядків                                          | `vite.config.ts`, ~13 рядків                                |
| Пакети для збірки            | 8                                                                        | 1                                                           |
| Перевірка типів              | автоматично через `ts-loader`                                            | окремо через `tsc --noEmit`                                 |

### Висновок

**Швидкість старту dev-сервера та HMR.** Vite запустився приблизно у 8 разів швидше (390 ms проти 3113 ms). webpack
перед стартом збирає весь проєкт разом із Bootstrap в один бандл, а Vite у режимі розробки нічого не збирає: браузер
завантажує ES-модулі напряму, а Vite лише перетворює кожен файл на льоту. Оновлення після змін обидва інструменти
виконують швидко, але webpack щоразу перезбирає частину бандла, а Vite оновлює лише змінений модуль. На більшому проєкті
ця різниця зростала б.

**Час і складність налаштування.** Конфігурацію webpack довелося писати вручну: точка входу, вихідна папка, окремі
лоадери для TypeScript, CSS і SCSS, плагін для HTML, налаштування dev-сервера. Для цього знадобилося 8 пакетів і знання
того, в якому порядку застосовуються лоадери. Vite підтримує TypeScript, CSS і SCSS з коробки, тож конфігурація зайняла
кілька рядків: порт сервера, папка збірки та відносний шлях `base` для GitHub Pages.

**Розмір і швидкість продакшн-збірки.** Vite зібрав проєкт приблизно в 4.5 раза швидше (871 ms проти 3980 ms). Загальний
обсяг файлів майже однаковий (320 KiB у webpack і близько 321 kB у Vite), бо основну частину займає Bootstrap. Але Vite
розділяє CSS і JS на окремі файли з хешами в назвах, тож браузер завантажує їх паралельно й ефективно кешує. webpack без
додаткового налаштування вбудовує CSS у JavaScript, а стилі застосовуються лише після виконання скрипта, тому він ще й
попереджає про великий розмір бандла.

**Підключення UI-фреймворку та TypeScript.** В обох випадках Bootstrap підключається однаково, через `import` у коді. У
webpack для цього потрібні `css-loader` і `style-loader`, у Vite нічого додатково не потрібно. TypeScript у webpack
обробляє `ts-loader`, який заодно перевіряє типи. Vite лише вирізає типи через esbuild (це значно швидше), тому
перевірку типів довелося додати в скрипт збірки окремою командою `tsc --noEmit`.

**Екосистема плагінів.** webpack існує давно і має найбільшу екосистему лоадерів і плагінів практично для будь-якого
завдання, а також тонке налаштування кожного етапу збірки. Vite новіший, але сумісний з плагінами Rollup і має власну
велику екосистему. Для цього проєкту жодних плагінів у Vite не знадобилося.

**Суб'єктивна оцінка.** Для невеликих SPA-проєктів на кшталт цього Vite зручніший: швидше стартує, швидше збирає і майже
не потребує конфігурації, тож можна одразу зосередитися на коді. webpack доречний у великих або старих проєктах, де
потрібен повний контроль над збіркою або вже налаштована інфраструктура. Водночас ручне налаштування webpack корисне для
навчання, бо показує, що саме відбувається під час збірки проєкту.
